# Opus City — Design & Engineering Decisions Log

Living document. Every phase appends its major decisions here so any future
session (or human) can pick up the project without re-deriving context.
Read this before touching the codebase.

## Project goal

A browser city simulation where the world keeps living whether or not the
player is present. The simulation is the product — visuals are intentionally
simple (stylized 2D top-down) so engineering effort goes into NPC AI,
economy, traffic, and emergent behavior rather than graphics.

## Stack

- **TypeScript + Vite**: fast iteration, strict typing catches the kind of
  state-shape bugs that are lethal in a system this size (250+ interacting
  entities, dozens of enums).
- **PixiJS v8 (WebGL)**: 2D renderer. Three.js/3D was explicitly rejected —
  spec section 19 says simulation depth matters more than visual fidelity,
  and 2D lets the performance budget go to sim logic instead of shaders.
- **Vitest**: unit + stress tests. No browser test runner is wired in yet;
  visual verification during development was done via a one-off Playwright
  smoke script (not checked in) rather than a permanent e2e suite — revisit
  in Phase 16/17 if regressions in rendering become a real risk.

## Architecture (spec section 28)

```
src/
  core/       Clock, EventBus, SeededRandom, shared geometry/id types
  world/      City data model, procedural WorldGen, RoadGraph + A*
  npc/        NPC data model, factory/population, UtilityAI, NPCSystem (LOD)
  economy/    (Phase 6+)
  traffic/    (Phase 5+, vehicle layer separate from NPC pedestrian movement)
  police/     (Phase 7+)
  social/     (Phase 8+ — relationships/memory, currently modeled as fields
              on NPC itself; may extract into its own system once crime/
              police start writing to it)
  events/     (Phase 9+)
  missions/   (Phase 10+)
  render/     Renderer — Pixi scene graph, reads sim state, never mutates it
  ui/         DOM-based HUD/inspector overlays
  sim/        Simulation — top-level orchestrator, owns the fixed tick loop
```

Hard rule enforced so far: **render code never mutates simulation state**,
and **simulation code never touches Pixi**. `Simulation.step()` is the only
entry point that advances world state; `main.ts` just reads from it each
frame.

## Simulation clock (spec section 3)

`SimClock` runs on simulated minutes, advanced by `advance(realDeltaSeconds)`
scaled by `timeScale`. Default: 1 real second = 1 simulated minute
(`timeScale = 1`); HUD buttons and number keys 1-5 switch between 1x/2x/5x/
10x/50x. `Simulation.step()` uses a **fixed 0.1s sim tick** accumulator
decoupled from render FPS, so simulation behavior doesn't change if the
browser drops frames — a standard fixed-timestep pattern, necessary here
because NPC decisions (path requests, activity switches) must not depend on
frame rate.

## Entity IDs and determinism (spec section 23)

IDs are generated by a module-global counter (`nextId()` in `core/types.ts`)
rather than per-simulation, which is simpler to write but means **only one
`Simulation` should be "live" (i.e. actively having entities created) per
process at a time** for id-determinism to hold. `Simulation`'s constructor
calls `resetIdCounter()` before generating the city, so two `Simulation`
instances built from the same seed produce byte-identical ids. This is a
deliberate scope cut — a fully self-contained per-simulation id generator
would be cleaner but wasn't needed yet since nothing currently runs two
simulations concurrently. Revisit if that changes (e.g. a "preview seed"
feature that generates a city without discarding the current one).

## World generation (spec section 17)

Fixed 9x7 block grid (`RoadGraph`), 8 districts laid out by hand
(`DISTRICT_LAYOUT` in `WorldGen.ts`) rather than procedurally clustered.
**Tradeoff**: a Voronoi/random district partitioner was considered but
risked producing unusable layouts (e.g. harbor district land-locked, or a
1-cell-wide sliver district) without a real constraint solver. The
hand-tuned layout guarantees sane adjacency (downtown central, harbor on an
edge) and is still procedurally *populated* — building placement, naming,
and stats within each district are all seeded-random. Connectivity is
verified at generation time (`ensureConnectivity`) and covered by tests;
world-gen throws rather than silently producing an unreachable district.

Buildings are placed per grid cell using a weighted random table per
district kind (`DISTRICT_BUILDING_MIX`). Civic buildings (hospital, police,
fire, government) are force-placed after the main pass to guarantee the city
is functionally complete even if the random pass under-produces them.

## Road network & pathfinding (spec section 7)

`RoadGraph` is a plain undirected graph (nodes = intersections, edges = road
segments) with A* pathfinding. Edge cost is **travel-time estimate**
(`length / effectiveSpeed`, where `effectiveSpeed` shrinks with
`edge.congestion`), not raw distance — this means congestion-avoidance falls
out of the same pathfinding call instead of needing a separate heuristic.
`congestion` is currently a static field NPCs don't yet write to; the
Traffic phase (5) will have vehicles update it per-edge based on occupancy,
at which point pedestrian and vehicle pathing both benefit automatically.

Arterial roads (every 3rd grid line) get 2 lanes / higher speed limit;
intersections with 3+ connecting edges get traffic lights. Light-phase
switching logic isn't wired to traffic flow yet — nodes carry
`hasTrafficLight`/`lightAxis`/`lightTimer` fields ready for the Traffic
phase to drive.

## NPC architecture (spec section 4)

**Rejected**: one independent update loop/timer per NPC (spec explicitly
warns against this, and it doesn't scale past a few dozen agents).

**Chosen**: a single `NPCSystem.update()` call per sim tick, iterating all
NPCs in a flat `Map`, with **4-tier LOD** based on distance to the camera/
player focus point:

| Tier     | Radius   | Update cadence                                   |
|----------|----------|---------------------------------------------------|
| high     | ≤250     | every sim tick — full pathfinding + movement       |
| medium   | ≤700     | every 2 sim-minutes, batched dt                    |
| low      | ≤1600    | every 10 sim-minutes, batched dt                   |
| abstract | beyond   | event-driven catch-up, no pathfinding, teleports    |

Abstract-tier NPCs skip movement and pathfinding entirely: instead of
walking, `abstractCatchUp()` figures out which schedule block they *should*
be in right now, teleports them straight to that block's building, and
bulk-applies need decay/income for the elapsed time in one step. This is the
"coarse event" simulation spec section 24 asks for — cost per abstract NPC
per tick is O(1) regardless of how much sim-time has elapsed, so a city of
thousands of off-screen NPCs doesn't cost more than a few hundred on-screen
ones. When the player travels toward them, their LOD tier upgrades and they
resume real pathfinding from their last teleported position — no special
transition code needed since `beginActivity()` already runs unconditionally
whenever the desired activity changes.

**Decision-making**: utility AI (`UtilityAI.ts`), not a full GOAP planner or
behavior tree. Each candidate activity (eat/sleep/socialize/leisure/work/
commit-crime) gets a score from need-deficit × personality trait; the
NPC's current scheduled block gets a flat baseline bonus so routines are
followed by default. A hysteresis threshold (only deviate if the winning
score beats the schedule by a clear margin) prevents needs "flapping"
between activities every tick. **Tradeoff**: this is simpler than GOAP and
can't chain multi-step plans (e.g. "steal money because rent is due in 3
days") — that kind of longer-horizon reasoning is deferred to the Economy/
Events phases, which will drive it via explicit event chains
(job loss → eviction → crime) rather than expecting the utility scorer to
discover it emergently. Documented in spec section 25's emergent-behavior
chain — we're implementing that chain as *systems reacting to events*, not
as something a single AI has to plan.

**Schedules**: generated once per NPC at spawn time based on occupation
(`NPCFactory.buildSchedule`), covering the archetypes spec section 5 lists
(office worker, police/fire shift worker, student). Schedule blocks are
static as authored, but the utility layer already allows runtime deviation
— dynamic schedule *regeneration* (e.g. permanently changing shift after a
job change) is Phase 6/9 work.

## NPC population (spec section 17 intersecting section 4)

`NPCFactory.populateCity()` assigns residents to homes and jobs to
workplaces at world-gen time, respecting building capacity. Occupation is
derived from the workplace kind (police station → police officer, hospital
→ doctor, etc.), with a flat 8% unemployed / 5% criminal roll for adults.
Current target is **250 NPCs** (per product decision); the code has no
hardcoded ceiling — LOD is what makes higher counts affordable, and scaling
up is a config change (`NPC_COUNT` in `main.ts`), not a rearchitecture.

## Testing (spec section 26)

- `tests/roadgraph.test.ts` — A* correctness, congestion routing,
  connectivity detection.
- `tests/worldgen.test.ts` — determinism, connectivity, civic-building
  completeness, capacity sanity.
- `tests/clock.test.ts` — time-scale math, day wraparound, weekend flags,
  periodic callback firing.
- `tests/simulation.stress.test.ts` — 250 NPCs × 5000 sim ticks (with the
  focus point sweeping so NPCs cycle through every LOD tier), asserting no
  NaN positions/money, needs stay in [0,100], no duplicate ids, no orphaned
  home/workplace references, activity always a valid enum value. A second
  test confirms two identically-seeded simulations produce byte-identical
  positions/money after 500 ticks.

Run with `npm test`.

## Traffic & vehicles (spec section 7, Phase 5)

`VehicleSystem` (`src/traffic/`) is a separate system from `NPCSystem`, not
a subclass of it — vehicles are their own entities with their own
pathfinding/movement, and NPCs merely "attach" to one while driving
(`npc.inVehicle`, `npc.pos` synced from `vehicle.pos` each tick in
`NPCSystem.syncFromVehicle`). This mirrors real life (the car exists
independent of who's in it) and keeps VehicleSystem reusable later for
ambient/AI-only traffic that no NPC owns.

**Car ownership**: 60% of employed, non-student NPCs get a car
(`NPCFactory.assignVehicles`), spawned parked at their home. **Drive vs
walk**: NPCSystem only requests a vehicle trip if straight-line distance to
the target exceeds `DRIVE_DISTANCE_THRESHOLD` (180 units) — short hops stay
on foot, matching how people actually behave (nobody drives two doors down).

**Traffic lights**: every node with 3+ connecting edges got a light at
world-gen time; `VehicleSystem.cycleTrafficLights` flips `lightAxis` every 2
sim-minutes. A vehicle checks the light's axis against the edge it's
entering from (`RoadGraph.axisOf`) and stops if they don't match — real
stop-and-go behavior, not a cosmetic light.

**Congestion feedback loop**: while driving, each vehicle increments an
occupancy counter on the edge it's currently traversing; after all vehicles
move, occupancy is converted into `edge.congestion` (capped, decays over
time when not reinforced) and written back onto the `RoadGraph` edge that
`findPath` already reads. This closes the loop described in the Phase 1
pathfinding notes: pathfinding didn't need to change for congestion-routing
to work, because both NPC and vehicle pathfinding already price it in via
edge cost.

**LOD interaction**: `VehicleSystem.update()` still moves every vehicle in
the city every tick regardless of its owner's NPC LOD tier — vehicle
movement is O(active trips), not O(NPCs), and is cheap enough (~150 vehicles
at current 250-NPC scale) not to need its own LOD yet. To keep abstract-tier
NPCs from visually diverging from a vehicle mid-drive somewhere else in the
city, `NPCSystem.abstractCatchUp` calls `VehicleSystem.parkAt()` to
snap-park the NPC's car at their new (teleported) location whenever an
abstract NPC's schedule block changes — this is a documented simplification
(the car "teleports" with its owner) rather than a bug: correct
full-fidelity vehicle simulation for entities we're not even
pathfinding-updating wouldn't be worth the cost. Revisit if this becomes
visible as a real artifact once traffic density/observer mode make it
common to watch an abstract NPC's car.

**Tests**: `tests/vehicles.test.ts` covers real pathing to a target,
absence of NaN across many ticks with several concurrent trips (congestion
active), and traffic-light axis toggling over time.

**Rendering**: vehicles are simple rectangles, red while waiting at a red
light, colored by vehicle kind. Not yet in the debug/inspector overlay —
Phase 14 territory.

## What's deliberately NOT built yet (upcoming phases)

Economy (beyond wage accrual), police/crime response, relationships/memory
writes (fields exist on NPC, nothing populates them yet), procedural
events, missions, save/load, observer/debug mode beyond the basic
click-to-inspect HUD, chaos testing, ambient (non-NPC-owned) traffic like
buses/taxis. Tracked phase-by-phase; see commit history for what landed
when.
